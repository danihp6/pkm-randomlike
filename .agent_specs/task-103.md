## 🎯 Scope

- **Task type:** data + engine rules (battle, run, save) + one UI reader + docs.
- **Role:** Dev.
- **Objective:** the catalogue gains **four waves** and every one of them is a rule
  the shipped seams already own:
  1. **The Tera Crystal** — a held item carrying a `teraType`, one `onStart`

     with the run keeping the colours it has **discovered**. This is the run's next
     `SAVE_VERSION` step, **22 → 23**, and the step carries both facts.
  4. **The three route consumables** — the exorcist's, the weather man's and the
     medic's effect in a bottle, used from the route bag on a member, writing
     `[Task-94]`'s modifiers or calling `[Task-95]`'s `healParty` — never a second
     implementation.
  One battle rule rides along because the catalogue now holds items a battle must
  refuse: `validateBag` rejects a route-only item.

- **Dependencies:** `[Task-87]` (the route use path: `src/engine/run/items.ts`'s

```ts
// src/engine/run/items.ts
export type CandyTreat = Readonly<{ stat: Exclude<StatId, 'hp'>; delta: 1 | -1 }>;

/**
 * The treat `colour` gives **this run**: one `rng.int` over `CANDY_STATS` then one
 * `rng.next()` against `CANDY_POSITIVE_CHANCE`, on
 * `Rng(hashSeed(`${seed}:candy:${colour}`))`, in that order. Pure and stable, so a
 * colour always moves the same stat in the same run. An unknown colour throws.
 */
export function candyTreat(seed: string, colour: string): CandyTreat;

/**
 * Spends one `itemId` on the route: a candy writes its treat on `memberId` and
 * records the colour; a route consumable applies its own effect to the whole run
 * (`heal` → `healParty`, `curse` → `withCurse`, `sky` → `withForcedField`), with
 * `memberId` ignored. Returns the SAME `run` object (no consumption) when the
 * member, the item or the stock is missing, and for a candy on a fainted member.
 */
export function useItemOn(run: RunState, memberId: string, itemId: string): RunState;

/**
 * True when spending `item` on `member` would do something. A route consumable
 * always applies (its effect is party-wide); a candy applies while the member is
 * alive; every shipped rule is unchanged.
 */
export function itemAppliesTo(member: RunPokemon, item: ItemDef): boolean;
```

- **The Tera Crystal's rule.** `handlersFor(item)` gains one branch, after `if
  (item.flee)` and before `if (item.recoil)`:
  `if (item.teraType) handlers = { ...handlers, onStart: teraCrystalHandler(item) };`
  and

  ```ts
  function teraCrystalHandler(item: ItemDef): NonNullable<EffectHandlers['onStart']> {
    const type = item.teraType!;
    return (ctx) => {
      if (ctx.owner !== ctx.source || ctx.owner.hp <= 0) return;
      if (ctx.owner.types.length === 1 && ctx.owner.types[0] === type) return;
      ctx.owner.types = [type];
    };
  }
  ```

  `onStart` fires for every live active at battle start and for each switch-in
  (`src/engine/battle/state.ts`, `turn.ts`), so the crystal re-applies whenever the
  holder takes the field. It draws **no RNG** and pushes no log line.
- **Precedence with a forme change.** `src/engine/battle/mega.ts` and `gmax.ts`
  re-run the start hooks after the forme change, so a crystal holder that Mega
  Evolves ends the call with `types = [teraType]`: **the crystal wins over the
  forme's own types**, deterministically, and a switch-out/switch-in repeats it.
  Write this into `docs/battle-spec.md` §9's clause (below), do not special-case it.
- **Infinite held items.** In `adoptBattleParty`
  (`src/engine/run/resolve.ts`), a returned snapshot keeps the battle's item when
  it has one and otherwise falls back to the run member's:
  `return fighter ? { ...member, fighter: { ...fighter, heldItem: fighter.heldItem ?? member.fighter.heldItem } } : member;`
  Nothing else in the fold changes; the battle's `consume`/`spend` still clear the
  **battle** fighter's item, so a berry still fires once per battle
  (`docs/battle-spec.md` §5's clause).
- **The candy's treat.** `useItemOn`'s candy branch:
  1. `treat = candyTreat(run.seed, item.candy)`; the target must be alive.
  2. The member's new map is the old one with `stat`'s value raised by `delta`; a
     value that reaches **0 is deleted** from the record (so `+1` then `−1` leaves
     no key and the save stays byte-stable).
  3. `updatePokemon(consumeItem(discoverCandy(run, item.candy), itemId), member')`.
  `statTreats` reaches the battlefield through `restoreFighter` → `createFighter` →
  `statAtLevel(..., treats)` and every stat re-derivation that reads a snapshot:
  `progression.ts`'s `adoptAtLevel`, `levelUpPokemon` and `evolvePokemon` HP
  recomputes, `memberEdits.ts`'s nature re-roll HP recompute, `mega.ts`'s and
  `changeBattleForm`'s stat recompute. Every other `statAtLevel` caller keeps its
  five-argument call.
- **The three route effects.** `useItemOn`'s route branch runs after the shipped
  stock check and the member lookup (the dropped-on member is only the **gesture's
  carrier** — the branch ignores its HP and status, but the id must still resolve,
  which the scene's drop always guarantees):
  - `{ kind: 'heal' }` → `healParty(run)` (party **and** box, HP/PP, never a
    resurrection, no status cure — the shipped stop);
  - `{ kind: 'curse' }` → `{ ...run, modifiers: withCurse(run.modifiers) }` (the
    same writer the exorcist's card calls; the hex is spent by the next battle's
    launch exactly as today);
  - `{ kind: 'sky', field }` → `{ ...run, modifiers: withForcedField(run.modifiers, field) }`
    (the same writer the weather man's card calls; `FORCED_FIELD_FLOORS` applies,
    and an unknown `field` id is the data bug the row's test pins).
  Every branch consumes exactly one unit and pushes no event and no battle line.
- **The battle refusal.** `validateBag` (`src/engine/battle/commands.ts`) gains one
  clause after the `held` one:
  `if (slot.item.candy !== undefined || slot.item.routeEffect !== undefined) return 'Only usable on the route.';`
  The string is an engine literal like every other refusal (never drawn — the scene
  throws it away, `docs/battle-spec.md` §5's `[Task-114]` note).
- **Determinism (D11).** The only new draws are the candy's two, **inside**
  `Rng(hashSeed(`${seed}:candy:${colour}`))` — one per distinct colour, minted, and
  never read by a battle, an encounter, a roster, a route or a plan. The crystal,
  the infinite held items and the three route effects draw nothing. No shipped
  fixed seed moves.
- Rules: no Phaser import in `src/engine/` and none in `src/data/`, no DOM, no
  allocation in a hot path (the crystal's handler runs once per send-out; the
  stat formula gains one map read per stat).
